# REVERSED 终态语义（gateway 权威侧）——借据反向映射所需输入

> 2026-08-11 · lending-bank-gateway（8022）出具
> 用途：回应 LFC-GW-CUTOVER 工单卡点②（lifecycel 自 2026-07-22 起催「REVERSED → 借据反向
> 终态映射细表」，dev 上 3 笔回调 FAILED 挂 `REVERSED_AWAITING_CORE_TERMINAL_SEMANTICS`，
> 其中 2 笔是 DISBURSE 放款冲正——**钱已退、借据仍 active**，是该工单唯一带资金敞口的一项）
> 断言均挂 file:line，取自 `app/domain/states.py` 与 `app/services/reversal.py`

## 0. 边界声明：什么是 gateway 能定的，什么不是

- **gateway 能定（本文档给全）**：REVERSED 因何产生、能从哪些前态进入、资金上到底发生了
  什么、哪些 business_action 永远不会出现 REVERSED。这些是网关侧的机器事实。
- **gateway 不能定**：借据（loan/借据状态机）该反向到哪个状态。借据状态机归属
  lending-core 与 lifecycel，网关不自造借据终态（这也是 gateway 现有实现的立场——
  `_reverse_original` 只翻自己的 order 台账，不外推业务态）。

所以本文档的定位是**映射表的左半列（资金事实）**，右半列（借据目标态）需 core 拍板。
左半列此前一直缺，导致 core 无法开工——现在补齐。

## 1. REVERSED 的三条产生路径

| # | 路径 | 触发方 | 是否有回调 | 代码锚点 |
|---|---|---|---|---|
| P1 | 上游主动调 `POST /api/v1/bank-funds/reversals` 全额冲正 | lending 侧（lifecycel / liquidation） | **无回调**，同步完成 | `app/services/reversal.py:75` |
| P2 | wedap 状态查询 / 回调回传 `txnStatus=REVERSED` | wedap | 有 | `app/domain/states.py:32` |
| P3 | 组合交易中途失败，wedap 柜面人工冲正后回传 REVERSED | wedap counter（人工） | 有 | `app/domain/states.py:96-98` |

P1 的关键机制（`reversal.py:127-170`）：wedap 冲正 HTTP 200 即**冲正指令受理成功** →
RVSL 单自身置 SUCCEEDED，**同一事务内**把本地原单翻 REVERSED。故 P1 下
「RVSL 单 SUCCEEDED」与「原单 REVERSED」原子成对，不存在只翻一半。

## 2. 能进入 REVERSED 的前态（含反直觉项）

`app/domain/states.py:99-136` 的转移表：

| 原单前态 | 可否 → REVERSED |
|---|---|
| ACCEPTED（已受理、外呼结果未落） | ✅ |
| SUBMITTED | ✅ |
| PROCESSING | ✅ |
| RESULT_UNKNOWN | ✅ |
| SUCCEEDED | ✅ |
| PARTIALLY_REVERSED | ✅ |
| FAILED / CANCELLED / EXPIRED | ❌ |

**这里有一条对借据映射至关重要、且反直觉的事实**：
**非终态单可以被直接冲正，不必先经 SUCCEEDED**（`states.py:96-98` 明确写了这个设计）。
即：借据侧**不能假设「凡收到 REVERSED，此前必然收到过成功」**。
若 core 的映射逻辑写成「先按成功入账、收到 REVERSED 再冲销入账」，遇到
ACCEPTED→REVERSED / RESULT_UNKNOWN→REVERSED 这两条路径就会去冲销一笔从未入账的分录。

对 FAILED/CANCELLED/EXPIRED 的处理（`reversal.py:53-62`）：gateway **记警告、不翻本地态、
不让请求失败**——即以 wedap 为资金权威、但本地台账保持原终态。这类分歧若发生，
gateway 日志会出 `cannot flip to REVERSED (wedap authoritative, skip local flip)`，
需人工对账；借据侧不会收到 REVERSED 通知。

## 3. REVERSED 是吸收态

`ABSORBING_STATUSES`（`states.py:143`）含 REVERSED，且 `_ALLOWED[REVERSED] = set()`
（`states.py:135`）——进入后不再接受任何迁移。重复冲正幂等跳过
（`reversal.py:51-52`）。故借据侧可以把 REVERSED 当**不可逆的最终事实**处理，
不必防「REVERSED 之后又变回成功」。

## 4. 按 business_action 分档：资金上到底发生了什么

| business_action | biz_type | REVERSED 的资金含义 | 会不会出现 REVERSED |
|---|---|---|---|
| COLLECT（出借人归集） | COLL | 归集款**整笔**退回出借人存款户，平台侧未留款 | 会（P1/P2/P3） |
| DISTRIBUTE（分发给用户） | DIST | 分发款整笔收回，收款人未留款 | 会 |
| DISBURSEMENT（放款，loans 域） | DISB | 放款款项整笔退回，借款人未实收 | **会——dev 上 2 笔资金敞口正是此类** |
| REPAYMENT（还款，loans 域） | RPMT | — | **永远不会**：还款受理响应值域只有 SUCCESS/PROCESSING/FAILED，还款失败不自动冲正、柜面只前向处置（`states.py:77-93`） |
| REFUND（部分退款） | RFND | — | 不产生 REVERSED；全额退款被硬护栏导流至冲正（`GW_422_FULL_REFUND_USE_REVERSAL`） |
| REVERSAL（冲正单自身） | RVSL | RVSL 单的 SUCCEEDED 表示「冲正指令受理成功」，被撤销的是它指向的原单 | RVSL 自身不会 REVERSED |

**冲正一律是全额**（`ReversalRequest` 带 `oriTxnAmount`，语义为全额冲正原交易）。
部分金额撤销走 refund，不产生 REVERSED。`PARTIALLY_REVERSED` 状态虽在枚举内，
但按现行口径（部分退款走 refund）**不会被使用**，契约未定。

## 5. 给 core / lifecycel 的映射表左半列（可直接消费）

```
事件：gateway 台账 order X 变为 REVERSED
可读字段：business_action / biz_type / amount / currency / biz_seq_no
        / 原前态（审计 upgrade_from，reversal.py:63,71）
资金事实：该 business_action 对应的资金动作已整笔撤销，钱回到发起前的位置
时序保证：REVERSED 不可逆；且不保证此前出现过 SUCCEEDED
```

右半列（借据目标态）需 core 按下列四问拍板，gateway 不代答：

1. DISBURSE 冲正 → 借据从 active 反向到哪个态？（「未放款」还是「已取消」？是否保留借据行）
2. COLLECT 冲正 → 撮合/出借份额如何反向？出借人额度是否释放？
3. 前态为 ACCEPTED / RESULT_UNKNOWN 的冲正（从未入账）→ 借据侧是否只清意图、不冲分录？
4. 若 gateway 出现「wedap 说 REVERSED 但本地 FAILED/CANCELLED」的分歧（§2 末），
   借据侧按谁为准？
